# Задача 3. Цена неизменяемости

*Средняя. Одна и та же строка, собранная двумя способами: как это делает
неизменяемая строка и как это делает буфер. Разница видна и в скопированных
байтах, и в секундах.*

## Что написать

Программу `03-concat.c` с функцией склейки и растущим буфером:

```c
char *str_concat(const char *a, const char *b);   /* новая строка в куче */

struct Buf {
    char  *data;   /* блок в куче или NULL */
    size_t len;    /* сколько байт занято, не считая завершающего нуля */
    size_t cap;    /* сколько байт помещается без переезда */
};

void buf_init    (struct Buf *b);
void buf_free    (struct Buf *b);
bool buf_reserve (struct Buf *b, size_t need);
bool buf_push_str(struct Buf *b, const char *s);
```

`str_concat` возвращает **новую** строку в куче: ни `a`, ни `b` она не меняет.
Владелец результата — вызывающий.

`buf_push_str` дописывает строку в конец буфера, расширяя его при
необходимости. После каждого вызова содержимое буфера — законная строка,
завершённая нулём.

Плюс три счётчика — обычные переменные уровня файла:

- сколько байт скопировала наивная склейка;
- сколько байт скопировал буфер;
- сколько раз буфер переезжал.

## Как устроен ввод

Ввода нет, число кусочков передаётся аргументом командной строки:

```sh
./03-concat 20000
```

Без аргумента берётся 20000. Программа собирает строку из `n` кусочков обоими
способами, замеряет время и печатает отчёт.

## Пример запуска

```
$ ./03-concat 20000
кусочков: 20000

наивная склейка: длина 20000, скопировано 200010000 байт, 0.119 с
буфер:           длина 20000, скопировано 20000 байт, переездов 13, 0.001 с

строки совпадают: да
```

Двести миллионов байт против двадцати тысяч — при одном и том же результате.
Время снято на учебной машине с санитайзерами; у вас числа будут другими, а
отношение — тем же.

## Сначала на Python

```python
s = ""
for i in range(20000):
    s += "x"
```

Наивная склейка на знакомом языке: каждый шаг создаёт новую строку.
Замерьте:

```python
import time
def bump(n):
    s = ""
    for _ in range(n):
        s += "x"
    return s

def bump_held(n):
    s = ""; keep = None
    for _ in range(n):
        keep = s
        s += "x"
    return s

for n in (25000, 50000, 100000):
    for f in (bump, bump_held):
        t = time.perf_counter(); f(n)
        print(n, f.__name__, round((time.perf_counter() - t) * 1000, 1), "мс")
```

Две функции отличаются одной строкой, а времена — в десятки раз, причём у
`bump_held` время учетверяется при удвоении `n`. Скажите, какая из двух ведёт
себя как ваша `build_naive`, и объясните, почему одна строка так меняет дело;
на лекции это разбиралось.

Правильный способ в Python — `"".join(parts)`, и он соответствует вашему
буферу.

## Требования

- `str_concat` не меняет ни одну из входных строк, поэтому обе объявлены
  `const char *`.
- Результат `str_concat` и результат сборки освобождает вызывающий. Утечек
  быть не должно ни в одной ветке, включая нехватку памяти.
- `buf_reserve` — единственное место, где вызывается `realloc`. Результат
  кладётся во временную переменную, при неудаче буфер остаётся корректным.
- Вместимость растёт удвоением. Место под завершающий ноль учитывается: после
  `buf_push_str` в буфере обязана помещаться строка длины `len` **вместе** с
  нулём.
- Счётчики увеличиваются по ходу работы, а не вычисляются формулой в конце.
- Санитайзер молчит, собирается без предупреждений.

## Проверьте себя

```sh
./03-concat --check
```

Он сам сравнивает то, что вернули ваши функции, с правильными ответами и
печатает `ok` или `ОШИБКА` на каждую проверку, а в конце — «сошлось N из M».
Код возврата не ноль, если что-то разошлось:

```sh
./03-concat --check && echo "склейка сошлась"
```

Тридцать проверок четырьмя блоками.

**`str_concat`.** Обычная склейка, две пустые строки, пустая слева, пустая
справа. Отдельно проверяется, что результат — новый блок: в него пишется буква,
после чего первый аргумент обязан остаться прежним.

**Буфер.** Состояние после `buf_init`, дописывание строки, дописывание пустой
строки, второе дописывание, завершающий ноль на месте, вместимость не меньше
`len + 1`, два `buf_free` подряд.

**Оба способа дают одну строку.** `build_naive("ab", 3)` и
`build_buffered("ab", 3)` обязаны дать `"ababab"`.

**Счётчики на тысяче кусочков по одному байту.** Наивная склейка обязана
скопировать ровно 500500 байт, буфер — ровно 1000. Первое число посчитайте на
бумаге до запуска: это сумма длин всех промежуточных результатов.

## Что посмотреть после того, как заработает

**Как растёт разрыв.** Запустите с 1000, 2000, 4000 и 8000 и выпишите
скопированные байты. У одного способа число растёт вчетверо при удвоении `n`, у
другого — вдвое.

**Без санитайзеров.** Соберите `make release` и повторите замер на 100000.
Санитайзеры замедляют оба способа, но по-разному — скажите, какой из них
страдает сильнее и почему.

**Во что обходится ноль.** Уберите из `buf_push_str` единицу, отведённую под
завершающий ноль, и запустите под санитайзером. Прочитайте отчёт и сравните
его с демонстрацией 09.

**Рост не вдвое.** Замените удвоение на `cap + 16` и посмотрите на число
переездов и на время при 100000. Формула из третьего дня предсказывает
результат — проверьте, что предсказание сошлось.

## Подсказки

- Длина результата `str_concat` — сумма длин. Сколько при этом просить у
  `malloc`, посчитайте сами: на защите попросят объяснить каждое слагаемое.
- Копировать удобно `memcpy`: она принимает число байт и не ищет ноль.
  Завершающий ноль ставится отдельной строкой.
- `buf_reserve` на пустом буфере получает `data == NULL`, и `realloc(NULL, n)`
  равносилен `malloc(n)`. Отдельной ветки не нужно.
- В `build_naive` временная переменная нужна по той же причине, что и в
  `vec_push` вчера: старый указатель нельзя терять, пока не получен новый.
- Если `--check` показывает верные строки, но неверные счётчики, посмотрите,
  не считаете ли вы завершающий ноль скопированным байтом.

## Зачем это здесь

Питоновская строка неизменяема, и `s += x` в цикле обязан был бы работать как
ваша `build_naive`. Отсюда правило «собирайте строку через `join`», которое
обычно запоминают без объяснения.
